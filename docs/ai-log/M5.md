# M5: Undo, redo and saved overrides

- Date: 2026-10-09
- Author: Claude Code (Opus 5.5); reviewer: maintainer
- Status: done (maintainer approved moving on to 1.0; manual checklist not yet confirmed)

## What was built
- `core/history.lua`: undo/redo steps. Each step is a set of changes. Changes from one gesture
  (one mouse press) merge, keeping each field's first `old` and latest `new`, so a world drag
  (x and y) undoes in one step. Steps are sealed after undo/redo, capped at 200, and there's a
  revision counter.
- `core/serialize.lua`: Lua literals that load back equal, including full-precision floats,
  `1/0`, `-1/0`, `0/0`, escaped strings, sorted keys, and cycle/type errors.
- `core/overrides.lua`: the override set, which forgets a field set back to its original;
  `render`/`parse` for `loupe_overrides.lua` (one line per value with a path comment); and
  `apply`, which only writes fields that still exist.
- `core/edits.lua`: the single write path, `set(target, key, value, { root, keys, gesture })`,
  with undo/redo kept in sync with overrides, and dirty tracking.
- `reflect.childKeys`; geometry entries, Objects picks and Inspector edits now carry `root`
  and `keys`.
- `loupe/storage.lua`: the file lives next to `main.lua` when running from a folder (via `io`),
  otherwise in the save directory. It's parsed with an empty environment, so it can only be data.
- `init.lua`: Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl/Cmd+Y, Ctrl/Cmd+S; Undo/Redo/Save buttons;
  an "unsaved changes" status; overrides loaded at attach and applied before the game's update,
  re-applied whenever a getter returns a new table.

## Numbers
230 specs (up from 171). Coverage: `core/` 99.4%, `ui/` 99.5%. 0 luacheck warnings across 58
files. Library ~2,400 lines; specs ~2,600 lines.

## Test-first evidence
history, serialize, overrides, edits and storage all failed on missing modules first. The
root/keys threading had 6 failures before the change; the attach integration had 10.

## What the gates and checks caught
1. **A data-corruption bug in the serializer (caught by the AI rereading it).** It used `#v` to
   decide which items to write without keys. With holes, `#` is unspecified: on LuaJIT
   `{1,2,3,4}` with `[2]` cleared reports 4, so `[3]` and `[4]` would have been written
   positionally and loaded back at indices 2 and 3. The first two test attempts didn't fail
   because their tables happened to report length 1. Probing both runtimes found a LuaJIT case
   that does, and the test now uses it. Fixed by measuring with `ipairs`.
2. **A wrong expectation in a spec.** The AI expected `["two words"]` to sort before `["end"]`.
   Corrected before running.
3. **Status text cut off (caught by an integration spec).** "1 saved override no longer matches
   the game" shared a row with three buttons and was cut to "1 saved over..". Status now has its
   own row; the save message is shorter, with the full path printed to the console.
4. **Two test bugs in the AI's own specs.** A leftover `draw` call wasn't reset, and
   `fake.calls = {}` replaced the table the stub records into (the stub keeps writing to the
   old one).
5. **Duplication avoided.** A list-append helper was about to be copied into three files.
   It became `reflect.childKeys`, next to `reflect.childPath`.
6. A scripted edit failed partway (the matched line had been reformatted by StyLua). The
   assertion in the edit script stopped it before any partial write.

## Verification beyond unit tests
Two separate real-LÖVE processes (scratch harness, outside the repo):
1. F1, select ship, drag `thrust` to 286, click Save. The file was written with
   `{ "game", { "ship", "thrust" }, 286 }, -- game.ship.thrust`.
2. A fresh process: the toolbar shows "loaded 1 saved override" and the Inspector shows
   `thrust 286`.

## Known limitations
- Overrides keyed through array indices (`rocks[3]`) apply to whatever is at that index next
  run (ADR 0003).
- Values read in `love.load` are applied too late; overrides are applied before the first
  `update`.
- Headless runs (`attach` does nothing) don't apply overrides, which keeps simulations
  reproducible.
- Edits made by the game itself aren't tracked, by design; only loupe's edits are.
